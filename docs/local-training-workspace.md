# Local attendance and academic backend

Migrations through `202610140029` are applied locally. These commands persist actual Supabase records; the ordinary application pages still use demonstration providers. No live policy is created by these migrations. Use synthetic accounts and approved test configuration to exercise this workspace.

Start Docker/local Supabase, `npx supabase functions serve`, and `npm run dev:client`, then open `http://localhost:5173/?trainingTest=1`. Complete account setup/current notice and staff MFA first. Choose a role you actually hold, select an accessible enrollment, and load saved records. Student clock buttons use fresh browser GPS; server timestamps determine attendance. Denied GPS/schedule attempts retain a receipt but create no session. Clock-out uses the original session placement/policy even after suspension; it becomes disputed and awards no automatic credit.

## Command sequence

Each command takes a UUID `command_id` plus a bounded JSON `payload`. The workspace supplies `enrollmentId` and the current `expectedEnrollmentRevision`. Keep an operation's original ID/payload after a lost response; reuse it exactly to replay the receipt. Different payloads with the same ID fail. The workspace keeps an in-memory operation while retrying, but does not persist it across a page reload. For deliberate API testing retain that ID yourself; never put credentials in a payload.

1. Coordinator configures approved DTR periods using `intrack_dtr_command`: `action: "configure_period"`, `periodKey`, `startsOn`, `endsOn`, `approvalReference`. Dates are explicit and bounded to 63 inclusive days; overlapping periods fail. Published period rows are immutable. Every configured break explicitly includes `paid:true` or `paid:false`; break windows must lie within the shift and cannot overlap. Use a period key matching the requirement's `instance_key` when that DTR will satisfy a configured requirement occurrence.
2. Student generates a completed period using `action: "generate"`, `periodId`. The server includes every relevant nonvoid session, rejects unresolved sessions/requests and freezes source revisions. Then submit with `action: "submit"`, `dtrId`, `expectedDtrRevision`.
3. Assigned adviser approves with `action: "approve"`, `dtrId`, `expectedDtrRevision` or requests revision with `action: "request_revision"` and a reason. Approval checks complete current coverage and overlaps, splits intervals at Manila midnight, merges unpaid-break overlap and caps total daily credit across deterministically ordered shifts. Approved hours come from the ledger, not from session status or browser totals.
4. Student task submission uses `intrack_academic_command`: `action: "submit"`, `kind: "task"`, `taskDate`, `content: { "description": "Actual activity" }`. Adviser review uses `kind`, `artifactId`, `expectedArtifactRevision`, `action: "approve"`, `"request_revision"` or `"reject"`. Revision/rejection needs a reason. Resubmission supplies the original `taskKey` and current `expectedArtifactRevision`; it creates a new immutable version.
5. Journal submission uses the same command with `kind: "journal"`, `requirementId` and `content`. Its frozen requirement recurrence must explicitly provide `startsOn`, `endsOn`, `requiredFields`, and `requireApprovedDtr`; recurring `items` store those fields on the matching occurrence. `allowNoActivity` must be explicitly true to permit no approved tasks. All approved tasks and approved overlapping DTRs are resolved by the server. The required reflection fields and dates are not guessed.

## Exceptions, corrections and missed punches

`intrack_attendance_exception` supports student `request` with `placementId`, `kind` (`location` or `schedule`), `allowedActions`, `startsAt`, `endsAt`, `reason`; exceptions are bounded to 31 days. Coordinator `approve`/`reject`/`revoke` takes `exceptionId`, `expectedExceptionRevision`, reason. Exceptions never substitute for current training clearance.

`intrack_attendance_correction` supports student `request` with `sessionId`, `expectedSessionRevision`, `clockInAt`, `clockOutAt`, attached owned `evidenceDocumentId`, reason. Adviser `approve`/`reject` takes `requestId`, `expectedRequestRevision`, `expectedSessionRevision` and reason. Out-of-schedule corrections require a current coordinator-approved scoped exception; future/overlapping intervals fail. Coordinator `void` requires session/revision, attached evidence and reason. Resolve a pending correction before voiding.

`intrack_reconstruction_command` supports student `request` with placement, historical timestamps, evidence and reason, then assigned-adviser `approve`/`reject` with request/revision and reason. Approval requires recorded historical active clearance for that placement, a confirmed policy and a valid nonoverlapping interval. The result is pending evidence, not an automatic credit.

Attendance corrections/reconstruction invalidate all current enrollment DTRs/credits and current journal/portfolio approval eligibility conservatively. Previous frozen snapshots and decisions remain. Generate and review replacement DTR versions to recalculate the complete affected daily allocations. Completed enrollments require explicit reopening before correction/revocation. Withdrawn enrollments can resolve and review historical work while remaining withdrawn. Corrections, reconstruction and DTR approvals must stay inside recorded historical active-clearance windows; a schedule/location exception cannot authorize training after suspension or withdrawal.

Resolution-file API sequence: `intrack_resolution_file_command(command_id,"reserve",payload)` with current enrollment revision, `name`, `mimeType`, `bytes`; upload the exact bytes to private `ojt-documents` at returned `path` with `upsert:false`; invoke `requirement-files` with `action:"finalize_resolution"`, `role:"student"`, `documentId`, a new finalization `commandId`, and payload containing enrollment/revision/document ID. The worker measures MIME/size/hash before caller-authorized attachment. It does not accept client hashes as validation.

## Evaluation rubric and evidence

A coordinator calls `intrack_publish_rubric` against an unpublished source policy with `policyId`, `kind` (`midterm`,`final`,`company`), `title`, approval reference, `calculationRule: {"mode":"sum_points"}`, and ordered `criteria: [{"label":"Approved criterion","maxPointsHundredths":2000}]`. These numbers are examples of the API representation, not an official rubric. The supported calculation is an unweighted exact point sum; weighting/pass thresholds need additional approved implementation.

Policy publication accepts an evaluation requirement with reviewer `adviser` and recurrence containing the source `rubricTemplateId`, `evaluationStartsOn` and `evaluationEndsOn`. It copies the rubric/criteria into the newly frozen policy and shares a copied rubric only when requirements explicitly reference the same source. Evaluation current versions remain separate by requirement occurrence, including multiple final-stage forms; use the copied criterion IDs from `intrack_list_assessments`, never the old source IDs. Requirement definitions cannot be added to an already published policy.

For evaluation/portfolio files, use `intrack_artifact_file_command` to `reserve` with `requirementId` and bounded metadata, immutable Storage upload, then Edge `requirement-files` action `finalize_artifact` with the exact requirement/enrollment/revision/document. Generic requirement approval cannot approve these academic artifacts.

Evaluation submission uses `intrack_evaluation_command` with `action:"submit"`, exact requirement/document IDs, evaluator name/affiliation, `evaluatedOn`, and `scores:[{"criterionId":"copied criterion UUID","pointsHundredths":1500}]`. The server requires every criterion exactly once, rejects foreign/duplicate/out-of-range scores and freezes normalized evidence/rubric identity. Assigned-adviser approval requires current artifact revision, `signedEvidenceVerified:true`, `scoresVerified:true`, and a factual review reason. Verification assertions are protected staff decisions and are recorded with the content hash; student entry alone provides no approval. No supervisor login exists.

## Portfolio, requirement bindings and completion

The portfolio requirement must use evidence type `portfolio`, reviewer `both`, and recurrence `contents` listing all 32 supplied catalog IDs exactly once with explicit `mandatory` booleans. The IDs are returned by `intrack_list_assessments`. This explicit component configuration is required; the global catalog does not silently impose a policy on existing enrollments.

Upload a real complete portfolio PDF through the artifact-file pipeline. `intrack_portfolio_command` student `submit` requires `requirementId` and `documentId`. The server checks hours, stage gates and unresolved records, then gathers approved current documents/DTRs/journals/evaluations plus waivers and credits into a frozen manifest. It references immutable existing bytes rather than signed URLs. This command does not generate a PDF.

Assigned-adviser review, then a separate coordinator review, uses `action:"approve"`, `role`, `artifactId`, `expectedArtifactRevision`, factual `reason` and `verifiedContentIds` containing every configured mandatory section checked against the actual PDF. Adviser approval leaves Under Review. Coordinator approval requires that same manifest and a different reviewer; it produces Approved. `request_revision`/`reject` clear current approval eligibility and preserve history.

`intrack_bind_specialized_requirement` attaches an approved exact academic artifact to its requirement occurrence using `requirementId`, `expectedRequirementRevision`, `artifactId`. DTR/journal/evaluation bindings currently require adviser-only review plans; portfolio requires both. Unsupported plans fail rather than being silently shortened. The binding rechecks live artifact status/revision; a later correction/revocation makes it unresolved.

Coordinator `intrack_finalization_command` with `action:"complete"` and reason rechecks approved hours, all configured stage gates, portfolio/source/credit identity and unresolved attendance. It writes an immutable completion summary, sets the enrollment outcome and completion time, and preserves historical decisions. `action:"reopen_completion"` requires completed work and a reason; it returns to Portfolio with revoked attendance authority and fresh portfolio decisions required. Completed summaries remain historical.

`intrack_revoke_approval` supports `kind` task/journal/evaluation/portfolio/dtr/requirement, exact `artifactId`, current `expectedArtifactRevision` and a reason. It is coordinator-scoped, forbids self changes and completed work, invalidates dependent current decisions, and pauses active clearance. The accepted historical MOA can be withdrawn even when a newer copy is pending; the revoked copy cannot satisfy a clearance gate again.

## Local database recovery verification


ode scripts/verify-local-database-recovery.mjs dumps the application/public/Auth/Storage-metadata schemas, creates a separate database, restores ownership/permissions using the local platform administrator and compares every selected table's row hash. It never resets or replaces the original database and refuses sources over its 128 MiB local test limit. The executed test matched 97 tables. Backups and failed/successful isolated databases are retained for operator inspection. The current tool does not restore migration history, file-object bytes, platform services or a separate host, so the combined recovery gate remains unchecked.
